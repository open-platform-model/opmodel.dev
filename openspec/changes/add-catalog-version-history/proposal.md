## Why

A module author on the Catalogs tab cannot tell whether a member or a field is new, changed or gone in the minor they read. docs-kit phase 1b (`add-version-history`, contract C13) makes `opm-docs pull` compute that history from the pulled segments and write it beside them as `site/.bundles/<project>/history.json`. This change is the site's half: read that file and show it, never compute it. `docs-kit DESIGN decision 12` limits the scope to badges and a "Changes in X" list; there is no diff view.

## Gates

Named as in docs-kit's `docs/orchestration.md` (PR #13, `plan/phases-1b-2-3`).

- **Sections 1 and 2: no gate.** They build and test against fixture bundles and a hand-written `history.json` that follows C13 as `add-version-history` `design.md` D4 shows it. The real build is unchanged: the real lock has no `history` entry, so no page gets a badge.
- **Section 3: G1b**, `add-version-history` released (expected docs-kit `v0.3.0`: its release-please PR merged by the owner, binaries and `checksums.txt` on the GitHub release). Section 3 also needs the immediate `chore(site)` PR pinning opm-docs `v0.2.1` merged first (it touches the same Dockerfile lines and lint fixtures).

## What Changes

- `gen-mounts.sh` mounts `*/history.json` beside each tab's segments; `gen-catalogs.sh` checks the file's SHA-256 against the lock's `history` entry and fails naming both digests when they differ; a project with no entry gets no badges.
- The catalogs adapter puts the page's member history (by FQN) and its kind's `removed` and `lineage` slices into `params.catalog.history`.
- New partials under `layouts/_partials/opm/`: one badge under a member's title ("Added in X", "In <floor> or earlier", "Unreleased", "Changed in X" for the page's own segment, "Newer version" linking the newest apiVersion's page in the same segment); a page-end "Changes in <segment>" list, one line per field change, worded more cautiously for a pair compared in `paths` mode; "Removed in X" entries on a kind index linking the page in its last segment. Nothing inline in the spec code block.
- Fixtures: the three fixture segments' `data/catalog.json` gain real `fqn`s and `spec.fields` and the members the badges need; check cases for each badge, the list, a digest mismatch and a `paths`-mode pair.
- `site/Dockerfile` pins the docs-kit release carrying `add-version-history` (version and SHA-256 together, C12), and the fixture lock is regenerated by that tool.

## Impact

- **Files.** `site/Dockerfile`, `site/scripts/{gen-mounts,gen-catalogs,gen-stamp,test-site}.sh`, `site/catalogs/_content.gotmpl`, `site/layouts/catalogs/{list,single}.html`, new `site/layouts/_partials/opm/history-{badge,changes,removed}.html`, `site/assets/css/opm/` (one new file for the badge), `site/tests/fixtures/bundles/**`, new check cases under `site/tests/checks/`, `site/tests/browser/` (a member with a badge and a list), `README.md`, `AGENTS.md`.
- **Build inputs.** Gained: one file per tab project, `history.json`, at the digest the lock records. The pinned `opm-docs` moves to the release carrying `add-version-history`. No theme file is newly overridden.
- **Published URLs.** None added or removed. The version set is unchanged; catalog minors are not site versions and 0021:OQ15 is not touched.
- **Source repos.** None. catalog_opm's bundles already carry every field the history reads (C10 `fqn`, `spec.fields`).
- **Depends on.** The immediate `chore(site)` PR (opm-docs `v0.2.1` and the `link-slashless-*` conformance fixtures). docs-kit `add-version-history` released (G1b) for section 3.
- **Delivery.** Two PRs, as `add-catalogs-tab` did: sections 1 and 2 may merge before G1b (no real output changes without a lock `history` entry); section 3 merges after G1b and carries the archive.
